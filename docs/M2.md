# M2 — the app skeleton

*Status: in progress (started 2026-07-25). Exit test: **fresh phone, no Termux — install
the APK, get a running Debian machine with a shell, in under 5 minutes.***

M2 turns the proven engine into an installable Android app. No AI layer yet (that's M3):
just machines, honestly packaged.

## What ships

- **Kotlin + Jetpack Compose app**, dark cellar theme (the site's palette).
  Screens: Machines list → Create wizard (distro picker + live progress) → Machine detail
  (start/stop, live logs, exec box). Terminal (ttyd in a WebView) is a stretch goal —
  the exit test needs a working machine, not a beautiful PTY.
- **The engine as a jniLib.** The same static Go binary, named `libcellar.so`, exec'd
  from `nativeLibraryDir` (the only W^X-legal home for it). One foreground service owns
  every engine invocation; UI talks to the service, service talks JSON to the CLI.
- **proot as *two* jniLibs** — `libproot.so` + `libproot_loader.so`. proot normally
  extracts its embedded loader to a temp file and execs it, which W^X forbids inside an
  app, so the loader ships as its own file and `PROOT_LOADER` points at it. Built from
  `termux/proot` (the only lineage with Android's sysvipc/seccomp/link2symlink patches);
  recipe, pinned tag and GPL corresponding-source notes live in `proot/`.
- **CI builds the APK** (GitHub Actions; never on a phone). Debug APKs as artifacts on
  every push; install on device via `gh run download` + the system installer.

## Engine v0.2 — app-proofing (prerequisite, done on-device first)

The engine currently shells out to the host `tar` for extract/export. An APK has no
`tar`. Rather than vendoring busybox (a whole second native binary + proot-wrapped
invocations), extraction moves into the engine itself:

1. **Pure-Go extraction**: stdlib `archive/tar` + the pure-Go `ulikunitz/xz` decoder
   (first and only module dependency — the "zero deps" line in the docs gets updated to
   say so honestly). Hardlink entries are materialized as **file copies** — kills the
   Android hardlink ban (field note #3) without proot's help, at the cost of a few
   dozen MB per rootfs. Symlinks pass through untouched; unknown/device entries are
   skipped; suid-style modes are normalized on the way out (field note #4 baked in).
2. **Pure-Go export**: stdlib `archive/tar` + `compress/gzip`. No shell-outs left.
3. **Path overrides already exist** (`CELLAR_HOME`, `CELLAR_PROOT`); the service sets
   them to app-private paths. `PROOT_TMP_DIR` follows `TMPDIR` as it already does.

Result: the engine's runtime needs exactly one external binary — proot.

## App architecture (deliberately thin)

```
MainActivity (Compose) ──bind──▶ CellarService (foreground, specialUse)
                                   ├─ EngineRunner: ProcessBuilder(libcellar.so …),
                                   │    env: CELLAR_HOME=filesDir/cellar,
                                   │         CELLAR_PROOT=nativeLibDir/libproot.so,
                                   │         TMPDIR=cacheDir
                                   │    stdout JSON → state flows; stderr → progress
                                   └─ wake lock while any machine runs
```

- minSdk 29 (Android 10), targetSdk 35, arm64-v8a only, `extractNativeLibs=true`,
  16 KB page alignment on every native binary.
- No database: `cellar ls --json` *is* the state. The app renders engine truth instead
  of mirroring it.
- Create wizard progress = the engine's stderr lines, streamed as-is. Honest > pretty.

## What the research changed (2026-07-25)

The static-proot investigation turned up a landmine that reshapes the packaging, plus
two engine defects the Android review lens confirmed on-device:

1. **proot needs its loader as a separate file** (above). A single static proot binary
   cannot work in an APK, no matter how it's built — worth knowing before writing the
   service, not after.
2. **`guestEnv` stripped `PROOT_LOADER`.** The engine builds a clean environment for
   guests; it would have discarded exactly the variable the app must set. Fixed and
   tested before the app could ever hit it.
3. **`/dev/shm` and orphaned daemons** — see field notes 7 and 8. Both fixed with
   on-device verification (the second with a measured A/B).

## Risks, named

- **proot outside Termux** is the technical risk (Termux patches, seccomp behavior,
  tmp-dir assumptions). Mitigation: UserLAnd proves it possible; the research memo picks
  the exact build; step 2 tests proot from a non-Termux path before any UI exists.
- **Slow iteration loop** (edit → push → CI → download APK → tap install, ~5 min).
  Mitigation: everything testable without the APK stays in the engine + unit tests;
  the app layer stays thin on purpose.
- **Phantom process killer** applies to the app's children too. Same discipline as the
  CLI: one proot per running machine; the guided "disable child process restrictions"
  screen is M3 scope but the foreground-service + wake-lock basics land here.

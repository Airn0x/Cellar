# M3 — the AI layer: two modes, a catalog, and chat

*Status: in progress (started 2026-07-25).*

M2 proved a phone can host machines. M3 is what makes Cellar a **product** instead of a
distro installer: the moment the app opens, a person who has never used Linux can get an
AI agent running, and a person who lives in a terminal can get out of the way.

## The two front doors

Every user picks one of these on first run (and can switch any time):

**Terminal mode** — "give me a shell, I'll do the rest." A machine plus a command
console. The app is just the box. This costs almost nothing to offer since the engine
already does it, and it's what anyone following a tutorial wants.

**Catalog mode (default)** — "I want to run *X*." One tap installs a verified stack into
a machine that's created for them if needed. No distro decision, no package manager, no
shell.

The design rule: **catalog mode must never be a dead end.** Anything installed by a tap
is inspectable and modifiable from the console, and nothing the catalog does is magic
that the CLI can't also do.

## The catalog

A stack is a folder with `meta.json` + `apply.sh` (already how the engine works). M3
enriches the metadata so the UI can be honest:

| field | why |
|---|---|
| `category` | agent · harness · runtime · service · model · chat |
| `size` | plain-language footprint ("~250 MB, few minutes on 4G") |
| `verified` | **has this been run on a real phone by us?** |
| `needs_key` | env var the stack requires (e.g. `ANTHROPIC_API_KEY`) |
| `chat` | headless command that takes a prompt — makes the stack chat-capable |
| `distros` | constraint, already present |

### The verified flag is the point

We have already found that npm breaks under proot's seccomp fast path and that Python's
multiprocessing needed `/dev/shm`. A one-tap install that fails is worse than no button.
So the catalog ships **two visibly separate tiers**: verified-on-device, and
"community / not yet verified on a phone" behind a warning. The catalog grows at the
speed of verification, not the speed of wishing.

### Planned contents

- **Coding agents** — Claude Code ✅, OpenCode, Aider, Goose, OpenHands
- **Harnesses** — MCP server kits, scheduled research loops
- **Runtimes** — Python + uv ✅, Node ✅, Go
- **Services** — sshd ✅, code-server, tunnels (Tailscale/cloudflared)
- **Models** — llama.cpp, Ollama (charging-gated, honest about speed)
- **Chat UIs** — Open WebUI / LibreChat in a machine, rendered in the app's WebView

## Chat

The chat tab is what turns this from a developer tool into something usable by someone
who doesn't know what a rootfs is — and it's the natural home for keys, schedules and
(in M4) the phone bridge.

v1 is deliberately thin: **chat drives an agent that's already installed in a machine.**
The app runs the stack's `chat` command with the user's prompt and streams the output
back into the conversation. No API client in the app, no second implementation of tool
use, no way for the app and the machine to disagree about what's installed.

```
[you]  summarize the news in my repo
   ↓   cellar exec dev -e ANTHROPIC_API_KEY=… -- claude -p "summarize…"
[dev]  <streamed output>
```

Later (M4): a direct API path for people with no machine yet, and local models as the
offline fallback.

## Keys

API keys are encrypted with a key that lives in the **Android Keystore** (hardware-backed
where the device supports it), stored as ciphertext in app preferences, and injected as
environment variables at the moment a command runs. They are never written into a rootfs,
never captured in logs, and never included in an export. The engine already supports
`-e KEY=VALUE`, so this required no new engine surface.

## First run: compatibility and settings

An app cannot flip a system setting for the user — only detect state, explain, and
deep-link. So every item follows: **detect → explain why → one button → re-check.**

| item | what we can actually do |
|---|---|
| arm64 / Android version | detect and state plainly whether this device is supported |
| free storage | detect; warn before a 90 MB download that won't fit |
| notifications | standard runtime permission |
| battery optimization | system dialog, one tap — the highest-value one |
| OEM app-killers (Samsung, Xiaomi, Oppo…) | detect manufacturer, deep-link where allowed, otherwise show the correct steps *for that brand* |
| phantom process killer | **impossible for an app to change.** Explain, offer the Shizuku/ADB path for power users, and keep our process tree small enough that it rarely matters |

The screen's job is to make the phone's limits legible *before* something fails
mysteriously — the same honesty the website leads with.

## Scope boundary for this milestone

In: the two modes, catalog UI + richer metadata, chat v1, key vault, setup screen,
command console.

Out (M4): a real PTY terminal (needs ttyd or a PTY bridge — the console covers the
80% case first), schedules, the phone bridge, local models, tunnels.
